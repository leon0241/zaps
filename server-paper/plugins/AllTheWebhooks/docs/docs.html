All the Webhooks

Configure events in events.yaml, messages in messages.yaml, and webhooks in config.yaml. Docs are written to plugins/AllTheWebhooks/docs/. Generation runs on startup (if documentation.generate-on-startup), on reload (if documentation.generate-on-reload), or via /allthewebhooks docs generate.

Use the sidebar to browse documentation, events, and sub-events. Each event includes predicates and wildcard patterns for filtering.

Quick start

  1. Configure a webhook in config.yaml under webhooks.
  2. Choose an event from the Events section (e.g. player.death, player.join).
  3. Add a rule in events.yaml under events with message and optional conditions.
  4. Define the message in messages.yaml using placeholders from the event's predicates (including context-enriched fields like {world.environment}).
Example: notify on player death
# events.yaml
events:
  player.death:
    message: death_alert

# messages.yaml
messages:
  death_alert:
    content: "**{player.name}** died in {world.name}"
Example: only lava deaths
events:
  player.death.attack.lava:
    message: lava_death

messages:
  lava_death:
    content: "**{player.name}** tried to swim in lava in {world.name}"

Event key hierarchy

Event keys use dot notation and support wildcard matching. More specific keys match before less specific ones.

How matching works

  • player.death.attack.dryout.player — matches only that exact death type.
  • player.death.attack.* — matches all attack-type deaths (cactus, lava, etc.).
  • player.death — matches any player death.

Sub-events

Some events (e.g. player.death, entity.damage.player) have sub-events discovered from registries and enums. Sub-events inherit predicates from their base, are shown in compact form under the base, and can be referenced under multiple logical groups (e.g. player.death.attack.lava under both player.death and player.death.attack.*).

Event keys are discovered at startup from Bukkit/Paper registries and enums. Death types, damage causes, and other sub-events are scanned dynamically.

Message structure

Event rules set message: <key>; that key is looked up in messages.yaml. The content template uses placeholders like {player.name} — each event's predicates can be used as placeholders. Predicates include event-specific fields (e.g. death.message, damage.amount) plus context-enriched fields from entities in scope: when an event has a World, Player, or Block, fields like {world.environment}, {player.name}, {block.type} are available automatically. See Entity field reference for the full list. Optional username per message sets the webhook display name; see Webhook display name.

Example
events.yaml
entity.damage.player:
  message: player_damaged

messages.yaml
messages:
  player_damaged:
    content: "{player.name} took {damage.amount} damage in {world.name}"

Conditions

Add conditions to event rules to filter when the webhook fires. Each condition key must match a predicate from the event. Predicates include event-specific fields and context-enriched fields (e.g. world.environment for deaths in the Nether). See Entity field reference and each event's predicates for what is available.

Available operators

  • equals — exact match (string or number); equals with a list matches if value equals any item
  • not — value not in list
  • greater-than / less-than — numeric comparison
  • greater-than-or-equal / less-than-or-equal — numeric comparison (inclusive)
Example: only drownings
events:
  player.death:
    message: death_alert
    conditions:
      death.message.key:
        equals: death.attack.drown
Example: exclude fall damage
events:
  entity.damage.player:
    message: player_damaged
    conditions:
      damage.cause:
        not:
          - FALL
          - FALLING_BLOCK
Example: only deaths in the Nether
events:
  player.death:
    message: nether_death
    conditions:
      world.environment:
        equals: NETHER
Example: numeric comparison (damage threshold)
events:
  entity.damage.player:
    message: high_damage_alert
    conditions:
      damage.amount:
        greater-than-or-equal: 10

Webhook display name

For Discord (and compatible webhooks), the name shown as the message author can be set in three places. The first value found in the order below is used.

  1. Per message — In messages.yaml, add optional username to a message entry. Example: messages.player_join.username: "Join/Quit".
  2. Per event or defaults — In events.yaml, set webhook-username under defaults or on any event rule. Example: webhook-username: "Diamond Alerts".
  3. Per webhook — In config.yaml, add optional username under each webhook. Example: webhooks.default.username: "Server Alerts".

If none are set, the webhook uses whatever name is configured in the Discord (or provider) webhook settings.

Example
config.yaml
webhooks:
  default:
    url: "https://discord.com/api/webhooks/..."
    username: "Server Alerts"

events.yaml
events:
  player.break.block.diamond_ore:
    webhook: moderation
    webhook-username: "Diamond Alerts"
    message: diamond_mined

messages.yaml
  player_join:
    content: "**{player.name}** joined"
    username: "Join/Quit"

Placeholder transforms

Overview

Placeholder values can be transformed before substitution. Use {key} for the raw value, or {key|transform} / {key|transform:args} to apply transforms. If the key is redacted, [REDACTED] is substituted and no transforms run.

How chaining works

Transforms are applied one after the other, left to right. Each transform receives the output of the previous one. Separate transforms with | (use \| for a literal pipe inside a transform).

Example: {key|trim|lower|truncate:10} — first trims whitespace, then lowercases, then truncates to 10 characters.

Transform reference

TransformArgsDescription
trim—Remove leading and trailing whitespace
lower—Convert to lowercase
upper—Convert to uppercase
defaultfallbackUse fallback when value is empty or missing
truncatemaxLengthLimit length to maxLength characters
replaceliteral:replacementReplace literal string (no regex)
last-path-segment—Last segment of a path (e.g. world from path/to/world)
first-path-segment—First segment of a path
mapkey1:value1:key2:value2:...Exact match: if value equals key1, use value1; etc.
regexpattern:replacementJava regex replace; $1, $2 for capture groups; $$ for literal $

Use \: for literal colon in args (e.g. map:foo\:bar:baz).

Examples: simple to complex

Simple — single transform
{player.name|lower}

For player.name = Steve → steve

Default for missing values
{optional.field|default:Unknown}

If optional.field is empty or missing → Unknown

Map boolean to label
{world.hardcore|map:true:hardcore:false:normal}

For world.hardcore = true → hardcore; for false → normal

Extract last path segment
**{world.name|last-path-segment}** has been loaded

For world.name = 2026/02/hardcore-26/world → **world** has been loaded

Chained — trim, normalize, truncate
{chat.raw|trim|lower|truncate:50}

Trims whitespace → lowercases → truncates to 50 chars. Each step uses the output of the previous.

Chained — path segment then uppercase
{world.name|last-path-segment|upper}

For 2026/02/hardcore-26/world → world → WORLD

Regex — extract second-to-last path segment
**{world.name|regex:.*/([^/]+)/[^/]+$:$1}** has been loaded

For world.name = 2026/02/hardcore-26/world → **hardcore-26** has been loaded

Chained regex — map true/false
{key|regex:^true$:hardcore|regex:^false$:normal}

First regex: if value is true → hardcore. Second regex: if value is false → normal.

Invalid or unknown transforms

If the transform name is unknown or args are invalid, the value passes through unchanged. A one-time warning is logged per placeholder key on error.

Security

Regex runs with a 300 ms timeout. On timeout or exception, the resolver uses the untransformed value and logs a one-time warning.

Commands

Commands are available with the /allthewebhooks prefix. Permissions are configurable via config.yaml under commands.<name>.permission.

CommandPermissionDescription
/allthewebhooks reloadconfigurableReload config, events, and messages
/allthewebhooks statsconfigurableShow plugin statistics
/allthewebhooks validateconfigurableValidate configuration
/allthewebhooks docs generateconfigurableGenerate documentation HTML
/allthewebhooks fire <eventKey> [key=value ...] [--dry-run]configurableFire a synthetic event; optional key=value pairs for context; --dry-run for dry run

For fire: when no key=value pairs are provided, a synthetic context is used. Use --dry-run to test without sending to webhooks.

Configuration reference

config.yaml defines the plugin configuration. Main sections:

  • plugin — plugin-level settings
  • webhooks — webhook URLs and options
  • rate-limit — rate limiting (e.g. events-per-second)
  • execution — execution behavior (e.g. overflow-behavior)
  • redaction — redaction.enabled, redaction.fields
  • logging — log verbosity
  • documentation — generate-on-startup, generate-on-reload
  • commands — per-command permissions

Key options include: validate-on-startup, events-per-second, overflow-behavior. See the default config for defaults.

events.yaml structure

events.yaml configures event rules. Structure:

defaults

Global defaults for all events: enabled, webhook, webhook-username, message, require-permission.

worlds

Per-world overrides: enabled, events. Use when different worlds need different event behavior.

Per-event options

Each event can override rate-limit.events-per-second for that event.

Redaction

Enable redaction in config.yaml with redaction.enabled and redaction.fields. Redacted fields are replaced with [REDACTED] in messages; no transforms run on redacted values.

Pattern matching

Field patterns use dot notation. player.ip matches exactly; nbt.* matches nbt.foo, nbt.bar, etc.
